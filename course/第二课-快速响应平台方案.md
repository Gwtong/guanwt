京东社群电商快速响应【第二课】
1.存量链路的断点
1.1.计划型运转：所有决策隔天生效
第一课末尾的四个系统连成一条完整链路：机器人白天实时回传群消息，SCRM 夜间跑批完成群分类与打标，推荐策略管理据此定次日发品计划，第二天由机器人与群主按排期执行。
链路的每一环都通，但每一环都是隔天的。回传是实时的，消费回传数据的所有环节都是 T+1 的——群里此刻发生什么，系统要到明天才知道该怎么反应。

用户上午在群里说“有没有便宜点的枣子”，这条消息当天就躺在回传库里，最快也要等到次日发品才可能被回应，而消费冲动的窗口以小时计。快速响应平台要补的就是这个断点：消息进来的那一刻就识别需求、决定响应。
断点不在数据链路上，在响应时效上——链路通而响应断。
2.快速响应平台：定位与主链路
2.1.旁路挂接：只读存量，只写三处
平台不改造任何存量系统。四路只读：实时消息流（社群机器人回传）、群画像与试点白名单（SCRM）、商品候选（社群推荐接口）、当日发品排期（推荐策略管理）。会写入存量系统的动作只有三处，全部是响应出口：给社群机器人下即时推品指令（艾特场景）；在群主端 App 置顶荐品并发 Push 通知（非艾特场景）；替换下一次发品排期中的原计划品（非艾特场景）。

摘掉这个旁路，存量链路照常运转——第一课“扩展性建设、风险低”的判断，在读写关系上就是这样兑现的：只读四路数据，写入只有三处响应出口，不碰任何存量系统的决策逻辑。
2.2.主链路十步
一条消息从进入平台到完成响应，经过十步：消息接入 → 前置过滤 → 消息聚合 → BERT 相关性判定 → DeepSeek 需求解析 → 需求去重与频控 → 分流决策 → 商品获取 → 响应执行 → 数据回流。

十步不是平均用力：前六步都在回答“这条消息值不值得响应”，后四步才是“怎么响应”。第一课的五道痛点，每一道都在对应的步骤上被拆掉。

3.2.会话式聚合窗
用户口语习惯拆条发：先发“有没有”，隔一分钟再发“便宜点的枣子”。单条送判，哪条都判不准。聚合把同一群、同一用户的连续消息拼成一个“发言单元”，再送模型。

T_静默、T_上限、T_回看 三个参数均为策略配置项，以试点调优为准——窗口行为可调，切分原则不变。

4.2.BERT：行为由标注定义，不由提示词定义
BERT 是判别式模型，没有提示词。它对“什么算商品相关”的全部理解，来自标注规范与训练数据——标注规范就是这一层的需求文档，产品经理在这一层的工作就是把它写清楚。

判定输出置信度：≥ τ 进入解析层，< τ 直接丢弃、不落库。τ 是精确率与召回率的权衡，由试点期调定。
BERT 层的产品设计，就是标注规范＋阈值 τ 这两件事。
4.3.DeepSeek 解析：系统提示词
守门后的相关消息进入解析层，DeepSeek V4 Flash 按系统提示词输出结构化需求。系统提示词全文：
你是京东微信社群的用户需求解析引擎。输入是一段群成员发言（unit_text），
可能附带该用户近几分钟的历史发言（context_text）。该发言已被上游判定为与商品相关。
任务：把发言解析成结构化的购买需求。
 
只输出一个 JSON 对象，不输出任何其他文字：
{
  "category": "归一化品类。用最常用的品类词，如红枣/大枣/枣子统一为枣；无法归一时用原词",
  "keywords": ["发言中出现的商品关键词原文"],
  "intent": "四选一：want_buy（想买）/ ask_rec（求推荐）/ compare（比价）/ complain（吐槽）",
  "price_pref": "价格意向，如便宜的、百元以内；发言未提及则为 null"
}
 
判定规则：
1. 吐槽不是需求。对已购商品的不满（如“枣子怎么不甜”“上次买的洗衣液不好用”），
   intent 必须判 complain，即使句中出现了商品词。
2. 提及不等于想买。转发商品消息、议论别人买了什么，不判 want_buy；
   仅当发言表达获取意愿（想要、求链接、有没有、多少钱）才判 want_buy 或 ask_rec。
3. context_text 只用于补全 unit_text 的语义（如上文“有没有”＋当前“便宜点的枣子”），
   不得把上下文里已解析过的旧需求重复输出。
4. 不臆测。发言里没有的信息不输出，price_pref 宁缺毋滥。

5.需求去重、频控与分流
5.1.需求指纹与 24 小时窗口
聚合解决“一个人拆条发”，去重解决“一个群反复提”。需求指纹 = 群 id ＋ 归一化品类——“红枣”“枣子”“大枣”在解析层统一为“枣”，同指纹即同需求。

热度不是副产品：同一需求被多人提起，是选品优先级与群主参考的直接信号。
24 小时窗口是“同一波需求”与“新一波需求”的分界——周一想买枣和周三想买枣，是两次独立的消费意愿。
5.2.频控【不是新需求，本来就有频控】
活跃群一天可能冒出十几条需求，全响应就是刷屏骚扰。每群每日非艾特响应设上限 N_频控（策略配置项，以运营策略为准）；艾特响应不占额度——用户主动发起的应答不算打扰。

8.演示版边界：Mock 什么、怎么替
8.1.原则：复刻边界，不是复刻实现
真实系统跑在公司内网，演示版在公开环境复刻它。复刻的对象不是实现，是边界：应用层与 AI 能力层、推荐层、数据层之间隔着什么接口，演示版隔着同样的接口；接口契约（输入输出字段的约定）一字不差，接口内部的实现可以换。
每一个替身都要能说出它对应真实系统的什么——这是演示版经得起追问的全部底气。
8.2.整体形态与逐环节映射
消息回放器驱动一个前后端分离的 Web 应用（Cloudflare 部署）；AI 判定段调 Dify 工作流 API；商品匹配调应用内 Mock 推荐接口；数据底座是三张 Mock 表。

消息回放器是演示版的发动机：会话窗口、艾特即时处理、24 小时去重、频控，全是跟时间顺序有关的行为，静态数据演示不了“第 59 秒与第 61 秒的消息被聚成一个单元”这件事。回放器按时间戳重放消息流，这些行为当场跑给人看。
8.3.AI 判定段：Dify 工作流
工作流发布为 API，应用侧 POST 调用。内部三个节点：轻量模型节点判相关（BERT 替身）→ 条件分支（无关即终止）→ DeepSeek 节点解析。画布本身就把“便宜模型守门、贵模型只算相关消息”的成本结构可视化了。
接口契约与真实系统通用——请求 unit_text ＋ context_text，返回 relevant、confidence、category、keywords、intent、price_pref。艾特判定不进此接口：艾特是消息元数据里的确定性字段，分流路由在应用层做，AI 只管语义。
BERT 替身节点的提示词（演示版专用）：
你是商品相关性判定器。判断输入的群聊发言是否与商品或购买需求相关。
 
相关：提及具体商品或品类；表达想买、求推荐、比价、询价；对商品的评价或吐槽。
无关：寒暄、表情斗图、接龙报名、与商品无关的闲聊。
 
只输出 JSON：{"relevant": true 或 false, "confidence": 0 到 1 的小数}
 
解析节点的提示词与真实系统的 DeepSeek 系统提示词同源（见第 4 章），一字不差——演示版换掉的是守门层的实现，没有换任何一层的行为定义。
口径必须守住：真实系统的守门层是 BERT，行为由标注与训练决定，没有提示词；演示版用提示词模拟它的判定行为——是替身，不是原理。
