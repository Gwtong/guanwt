1.行业背景：社群电商
1.1.什么是社群电商
在中国，一般指在微信群进行商品交易的商业模式，通过社群的力量增加用户的粘性和购买转化率。
人：以下沉用户为主。这类用户时间较多，容易被意见领袖感召，比如快手主播家人群。
货：决策成本低、易形成从众效应的品。爆品逻辑。
场：微信私域场。

1.2.各大电商公司发展社群电商的原因
可以覆盖更多类型的客户。用户可能不会下载京东，但用户一定有微信。
社群存在群主与意见领袖。能够待在群里的有效成员，与群存在信任关系，可以有效降低群成员购买的"决策成本"。对于此类用户，社群场景更容易刺激销售。
可以与中心化渠道形成互补，增强用户粘性（美团外卖商家群、福利官群）。

1.4.群主怎么挣钱：CPS 与京东联盟/京粉
群主在群里发商品消息，收入主要靠 CPS。

CPS 是 Cost Per Sales 的缩写，意思是"按销售分润"。对广告主，只需为实际带来销售的部分付费，无需为曝光或点击买单，风险较低；对推广者，推广方式多种多样，比较灵活。

1.5.社群机器人
个微社群的痛点：个人微信无法统计数据。不借助其他手段，只能知道有多少个推客，不知道建了多少个群，更不知道群的活跃情况。
微信社群机器人，是一种特殊的微信账号，两大作用：①在微信社群中按照规则发送特定的营销信息；②通过技术手段统计群成员数及群成员特征（昵称+头像）。

微信社群机器人一般由专门的公司提供——此类公司对申请账号、腾讯风险规避等比较专业。微信不会提供个人微信群的数据，有意愿开展社群营销业务的公司，为了更好地获取群数据，就需要和此类公司合作，使用其机器人能力。这也是芬香客户端法人非京东的原因。

2.SCRM：用社群机器人实现群管理
2.1.CRM 与 SCRM
CRM 是 Customer Relationship Management（客户关系管理）的缩写，是一种通过技术、流程和策略来管理和增强企业与客户之间关系的方法和系统。
SCRM 是 Social Customer Relationship Management（社交客户关系管理）的缩写，是 CRM 的衍生概念，专注于利用社交媒体和网络社区来建立、维护和加强企业与客户之间的关系。
对群的分类管理，是 SCRM 的一种。

2.2.衡量标尺：群点击活跃率
如需衡量，则需标尺。社群渠道的转化量=【微信社群每群平均人数×营销资源人均曝光量×点击率】×【点击后客户端内转化率】。提升社群渠道效果，可以从群内指标入手，也可以从客户端内转化率入手——但后者①不如群内指标容易影响用户②是下游指标。从漏斗上游的群内指标入手是更佳选择。
点击率=人均点击量/人均曝光（PV）。无法知道人均曝光，就没法知道点击率。

只能寻找替代，造一个新指标：群点击活跃率=群营销资源的点击量/群人数。直观理解：群人数 100 人，投放相同数量的营销资源，总共被点击 30 次的群，肯定比被点击 10 次的群活跃。
群点击活跃率，是社群的北极星指标。

3.痛点：为什么一直没做群内需求的实时响应
3.1.前提：链路是通的
机器人可获取群消息并回传京东分析（见第 1 章），此前的用途止步于活跃统计。理论上，平台一直具备快速响应群内用户需求的能力，且快速响应对提升群的价值是公认的。
没做，不是想不到——是下面五道实现成本算不过来。
 
3.2.信噪比极低：全量分析等于把算力花在闲聊上
群消息绝大部分是寒暄、斗图、接龙、灌水，真实购买需求占比极小。捕捉需求意味着每条消息都要过一遍分析，绝大多数计算注定无效。23 万运营群、每群每天数百条消息的量级下，实时分析的成本与能捞回的需求量完全不成比例。
3.3.现有链路是离线批式：实时化等于重建一条链路
回传消息做活跃统计，T+1 跑批足够。及时响应意味着消息队列、流式处理、低延迟推理服务整套新建——为一个未验证收益的功能立项一条实时链路，工程投入过重。
3.4.识别不准的后果直接暴露在群里
意图理解错误就是机器人乱接话，负面体验当着全群发生，直接伤群氛围。前大模型时代，定制 NLP 要达到敢上线的准确率，标注与开发成本都很高。
3.5.机器人逐条读消息的观感与隐私敏感
实时接话等于向全群宣告"机器人在逐条分析你们说的话"，用户观感差、可能引发退群，隐私层面敏感。
4.转机：为什么现在可以做了
4.1.模型能力显著提升
2026 年模型能力显著提升，意图识别的错误率大幅下降，"乱接话当众翻车"的风险可控——识别质量这道约束松动，建设实时响应能力进入可考虑范围。
4.2.AI Coding 相对成熟
产品经理可以直接处理核心逻辑、快速呈现 demo 版本，并发等工程问题交由开发处理。验证一个想法，不再需要先重建一条实时链路——信噪比、峰谷配置、链路重建三道成本的算盘重新打得过来了。
4.3.本项目的风险特征适合 AI Coding
本项目属于扩展性建设，不改动现有线上服务；即使挂了，危害也低。这正匹配 AI Coding 产出代码的风险特征，适合作为落地试点。

4.4.项目目标
建设群内需求快速响应能力，在部分群试点，实现群点击活跃率的显著性提升（统计显著）。
4.5.关键系统与系统关系
快速响应能力不是从零建设。四个系统已经在运转，本项目的方案挂在它们之上——先看清每个系统管什么、彼此怎么连接，后面的方案才不悬空。

生产环境的本质：代码质量的下限由最坏情况决定，而不是由正常情况决定。
 
5.2.一行代码的上线旅程
生产环境的复杂性不只体现在代码本身，还体现在流程上。一个改动从提出到全量，完整链路：
需求评审 → 技术方案评审 → 开发 → 代码评审（CR）→ 单元测试 → 回归测试 → 压测（涉及大流量时）→ 灰度发布（先放 1% 流量观察）→ 监控确认 → 全量发布 → 值班保障
每个环节都有专人把关，任何一环发现问题都会打回。改一行文案也要走完整个流水线——不是效率低，而是数亿用户规模下，任何"小改动"都可能是事故源头。
流程的本质：用组织化的层层拦截，把单个工程师犯错的概率压到可接受范围。

第一类中 AI 生成的代码确实进了生产环境，但每一行都经过上一节的完整流水线把关，AI 只是把"写"这一环提速。第二类没有这套把关体系，产出物的风险完全由使用场景的容错能力兜住。
大厂 AI Coding 落在运营端，不是因为 AI 能力不够，而是因为运营端的容错结构允许"快速做出来、出了错人能接住"，这正好匹配 AI 产出代码的风险特征。

6.理念二：想清楚是前提
6.1.需求质量决定产出质量
AI 把"想法变成代码"的执行成本压到接近零，但输入的需求含混，产出的方案同样含混。自己都想不清楚要什么的人，AI 只会把这份不清楚放大成一个跑得起来的错误方案。
"想清楚"不是一种感觉，可以拆成三个可检验的问题：
问题
检验标准
反例
目标：为谁解决什么问题
能用一句话说出使用者和使用前后的差别
"做一个数据看板"——谁看？看了之后做什么决策？
边界：做什么、不做什么
能明确说出哪些需求这一版不做
什么都想要，做出来什么都不好用

有可验证的完成判据
"好用就行"——无法验收，无限返工
AI 抹平的是"把想法变成代码"的执行门槛，没有抹平"想清楚要做什么"的思考门槛。

Prompt 写得好不好是表象，需求想得清不清楚才是本质。

6.3.为什么产品能力穿越周期
技术周期更迭，被替代的始终是执行环节：从手写代码到框架，从框架到低代码，再到 AI coding，每一轮淘汰的都是"把明确需求翻译成实现"的工作。
"把一件事情想清楚"不在此列。它要求理解业务、理解用户、在约束下做取舍——这些输入存在于真实世界的沟通和观察里，不存在于任何模型的训练数据里。
产品经理穿越周期的原因：每一轮技术革命都在降低执行成本，从而抬高了"想清楚"的相对价值。

7.AI Coding 不是一次性玩具
7.1.有人用，就有迭代
一个工具只要真的被人使用，就会产生反馈：需求变化、场景扩展、边界情况报错。demo 演示完可以扔，工具必须改得动。
改得动的前提是知道改哪里。这就引出黑盒问题。
7.2.过程不能是黑盒
好的 AI coder 知道自己产出物里每一个功能点的产品逻辑：数据从哪来、按什么规则处理、异常时表现是什么。不需要读懂每一行代码，但必须能回答"这个功能为什么这样表现"。
自己都无法掌控产品的细节逻辑，使用者更不可能信任它。黑盒的代价不在第一次交付时爆发，而在第一次迭代时爆发——不知道改哪里、不知道改了会不会弄坏别处，只能推倒重来。
判断标准：使用者报了一个错，能不能在不重新生成整个项目的前提下，定位到是哪个功能点的哪条逻辑出了问题。

7.3.怎么保持白盒
白盒不靠读代码，靠工作方式。四个可执行的做法：
做法
具体操作
防住什么
功能清单
维护一份"功能点-逻辑规则"对照表，迭代时先查表
防止迭代时不知道改哪里、改了弄坏别处
分步生成
一次只让 AI 做一个功能点，确认逻辑后再做下一个

四个做法的共同逻辑：把验收单位从"整个项目"压小到"单个功能点"。功能点级别的掌控，人做得到；项目级别的整体掌控，谁都做不到。
白盒的本质不是看懂代码，而是把产品逻辑的验收权始终握在自己手里。
7.4.Vibe Coding 的迷惑性
纯粹的 vibe coding——只描述感觉、不掌控逻辑、产出全靠 AI 自由发挥——具有极强的迷惑性：门槛降得过低，让人误以为动动嘴就能做出好程序。
它真实的成本结构是：做出来的门槛确实降了，改得动的门槛一点没降。长期依赖 vibe coding，培养出的是不善于思考的人——恰好在"想清楚"这个不可替代的能力上退化。
Vibe coding 的门槛低在"做出来"，高在"改得动"；省掉的思考，会在迭代时连本带利还回来。
8.三个关键哲学：由 Agent 的本质推出
8.1.Agent 是什么
AI coding 工具的本质是 Agent：大模型 + 工具调用 + 循环。它读取指令，调用工具（写文件、跑命令、查资料），观察结果，再决定下一步，循环往复直到任务完成。
Agent 不是一个"更聪明的搜索框"，而是一个能自己动手、但带着三个天性缺陷的执行者。三个天性决定了和它协作的全部方法论：
天性
含义
直接后果
概率生成
同样的输入，每次产出可能不同
不加约束，技术选型、字段命名每次都在漂移
上下文有限
一次只能装下有限的信息，装不下整个项目
任务越大，它对全局的把握越失真
无状态
每轮对话都重新理解世界，不记得上次做了什么
项目知识不外置，迭代时等于换了个新人接手
三个关键哲学，分别对治一个天性：关键规则对治概率漂移，过程驱动对治上下文有限，双向引用对治无状态失忆。

8.2.哲学一：关键规则
关键规则：项目开始前用书面文件锁死的关键约束，Agent 每次工作前必须先读。类比装修：开工前定死水电走线图，而不是让工人每天按当天的想法重新排线。
锁什么，按不锁的后果倒推：
规则类型
锁定内容
不锁的后果
技术栈
语言、框架、库及版本
这次用 React 下次用 Vue，两次产出无法拼装
Schema
数据字段名、类型、口径
同一个"订单金额"在三处出现三个字段名，数据对不上
目录结构
文件放哪里、怎么分层
文件散落各处，迭代时找不到要改的东西
命名规范
函数、变量、文件的命名规则
同一个功能三种叫法，追踪链路断裂
禁区
不许动的文件与逻辑
改 A 功能时顺手"优化"了 B 功能，B 悄悄坏掉
规则文件一次写成、反复生效：Agent 每轮对话都无状态，但规则文件每轮都会被重新读取——规则是对抗概率漂移的锚点。
规则的作用不是限制 AI，而是把 AI 的概率发挥收敛到项目需要的方向上。

8.3.哲学二：过程驱动
一句话拿结果，指望"帮我做一个审核工具"直接产出成品。这条路的问题不是产出差，而是产出无法验收：几千行代码一次性出现，对不对、哪里不对、怎么改，全都无从下手——一步到位与黑盒是同一件事的两面。
过程驱动把一次交付拆成一条流程，每一步产出小、可检查、可打回：
阶段
产出
验收动作
明确需求
目标、边界、标准（理念二的三问）
人确认需求描述无歧义

人确认方案符合关键规则

每点用自备用例验收（理念三的做法）

端到端跑通全流程
流程同时化解了上下文有限的问题：Agent 不需要一次装下整个项目，每一步只装当前阶段需要的信息，把握精度不随项目变大而下降。
过程驱动的本质：把"一次赌一个大结果"换成"多次锁定小结果"。

8.4.哲学三：双向引用
双向引用：从 BRD 到上线产品之间建立逐层对应关系，每层向下可追踪、向上可回溯。链路长这样：
BRD（业务目标）→ PRD/功能清单（R-01、R-02…）→ 功能点（F-01、F-02…）→ 模块与文件 → 上线产品
正向引用：每个功能点标注它来自哪条需求；反向引用：每个模块能说出它为哪条需求服务。两个方向合起来，项目里不存在"不知道为什么在这里"的代码，也不存在"不知道做没做"的需求。
迭代时的收益具体到操作层面：
场景
无引用链
有双向引用
需求变更
"改一下审核逻辑"——AI 全项目乱找，改错范围
R-03 变更 → 定位 F-07 → 定位模块文件，指令写成"只改 F-07，不得影响 F-08/F-09"
代码存疑
一段代码不认识，不敢删，越积越乱
反向追到需求条目，需求已废弃则放心删除
新一轮对话
Agent 失忆，重新讲一遍项目背景
Agent 读引用链即恢复全局图景，无状态被外置记忆补上
引用链就是项目的外置记忆：Agent 记不住项目，但引用链替它记住——这正是对治无状态天性的答案。
双向引用的本质：给项目建立一条从需求到代码的可追踪链路，让每一次迭代都有精确的作用范围。

9.2.第①步：agents.md——先立宪法
agents.md 是项目的全局描述文件，也是项目宪法：声明这个项目做什么、产物如何组织、Agent 必须遵守什么。它是项目里的第一份文件，先于一切内容产物存在。
宪法里必须写进一条铁律：每产生一份新产物，必须建立与相关产物的双向引用，拒绝孤儿文件。一份文件如果没有任何其他文件引用它、它也不引用任何文件，它就是孤儿——Agent 下轮对话找不到它，迭代时它就是定时炸弹。
引用链不是事后补的台账，而是从第一份产物起就强制执行的准入规则。哲学三（双向引用）之所以能成立，靠的就是这一步把它写成宪法条款。
9.3.第②③步：BRD 与前端原型——把需求定到不能再歧义
BRD 声明要做的事情，必须细化到功能点级别，且 in scope 与 out of scope 同等重要。"做什么"写成功能点清单（F-01、F-02…），"不做什么"逐条列明。out of scope 不是客套话——没有它，Agent 会自作主张扩展功能，需求方会无限追加想法，两头一起失控。
BRD 定稿后，下一步不是建数据库，而是直接生成可交互前端，反复调整，直至功能满意。顺序有意为之：
 
传统顺序（先建库后做界面）

需求方对文字的确认是虚假确认——看得见、点得动的界面才能逼出真实反馈。原型定稿后，界面上有哪些数据，数据库字段就自然从界面倒推出来，下一步才有了可靠输入。
前端原型是需求确认工具，不是开发产物：它的使命是把需求钉死，钉死之后它的历史使命就完成了。

9.5.第⑦⑧⑨步：主子 PRD、开发计划、测试用例——方案先于代码
PRD 区分主子结构：主 PRD 起索引作用，子 PRD 负责实现。主 PRD 不写实现细节，只管三件事：有哪些功能点、每个功能点对应哪条 BRD 需求、实现细节在哪份子 PRD。子 PRD 一份对应一个（或一组）功能点，写清数据流转、处理规则、异常表现。
主子结构不是文档洁癖，是给双向引用建中枢：BRD 的需求编号、子 PRD 的功能实现、后续的代码文件，全部经主 PRD 这个索引互联。Agent 上下文有限，每次只需装载主 PRD + 当前要做的那份子 PRD，不必装下全部方案。
开发计划把子 PRD 排成实现顺序：先做哪个功能点、后做哪个、依赖关系是什么。测试用例在写代码之前就位，每个功能点配正常/边界/异常三类用例——验收标准先于代码存在，Agent 才没有"看起来能跑就算完成"的空间。

9.6.第⑩⑪⑫步：开发、测试、部署——过程驱动的收尾
⑩ 开发：一个功能一个功能开发，开发好一个，自测一下。单位是功能点，不是整个项目：实现 F-03 → 跑 F-03 的测试用例 → 通过才进入 F-04。这是哲学二在代码阶段的形态——每个功能点都是一次"锁定小结果"。
⑪ 全部功能跑完后，完整执行一遍全量测试用例。逐个自测通过不等于整体可用：后做的功能可能悄悄弄坏先做的功能，全量回归是唯一能发现这种交叉破坏的手段。
【playwright】前端测试是必要的。
⑫ 云端部署，点检。部署后逐项点检：核心流程在真实环境走一遍、数据读写正常、外部依赖连通。本地能跑和线上能用之间隔着环境差异，点检清单就是最后一道闸门。
上线不是流程的终点，而是迭代的起点——此时项目留下的宪法、锁定文件、主子 PRD、测试用例和引用链，就是下一轮迭代的全部起跳板。
